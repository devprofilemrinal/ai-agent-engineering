# Validating and Sandboxing Tool Execution

## Why this exists

The previous file established, mechanically, that a tool call — both which tool gets selected and what arguments it receives — is a generated, sampled output, not a verified, trustworthy instruction. This file is the direct engineering response: every `tool_use` block your code receives must be treated as untrusted input, subjected to exactly the discipline you'd already apply to any request arriving at a public REST endpoint from an external caller, because that is, structurally, what it is — content generated by a process outside your direct control, about to trigger real code execution if you let it.

## The mental model: the model is an untrusted caller of your internal API

This reframing does most of the work in this file. You would never take a JSON body posted to `/api/pods/restart` and execute it without validating the pod name exists, the namespace is one the caller is authorized for, and the request is well-formed — regardless of how much you trusted the client application that supposedly sent it. A `tool_use` block deserves identical treatment. The fact that it came from "your own" model, configured with tools you defined, doesn't change that the actual argument values were generated by a probabilistic process capable of producing something malformed, out of scope, or (in a more adversarial framing, covered further in Phase 11's guardrails discussion) something a manipulated conversation talked the model into requesting.

```mermaid
flowchart TD
    A["tool_use block arrives"] --> B{Schema-valid?}
    B -- No --> R1["Reject, return an error tool_result — do not execute"]
    B -- Yes --> C{Passes business-rule validation?<br/>e.g. namespace exists, resource within caller's scope}
    C -- No --> R2["Reject, return an error tool_result — do not execute"]
    C -- Yes --> D{Requires human confirmation? (file 4)}
    D -- Yes --> E["Hold for approval before executing"]
    D -- No --> F["Execute, in a scoped/sandboxed context"]
```

## Layer 1: schema validation

The `input_schema` you defined (file 1) constrains what's *syntactically* possible, but you still need to actually validate an incoming `input` block against it before use — the same way you'd validate a deserialized request body against its declared constraints rather than assuming a client always sends conforming data:

```java
public class ToolInputValidator {

    private final Schema schema; // a JSON Schema validator, e.g. from a library like everit-org/json-schema

    public ToolInputValidator(Schema schema) {
        this.schema = schema;
    }

    public ValidationResult validate(String rawInputJson) {
        try {
            JSONObject json = new JSONObject(rawInputJson);
            schema.validate(json);
            return ValidationResult.valid();
        } catch (ValidationException e) {
            return ValidationResult.invalid(e.getAllMessages());
        }
    }
}
```

## Layer 2: business-rule validation, beyond what a schema can express

A schema can express "this string must be one of `dev`, `staging`, `prod`," but it can't express "this specific caller is only authorized to act on `dev`," or "this pod name must actually exist in this namespace right now." These are business rules, checked with ordinary Java logic against your actual system state — no different from authorization and existence checks you'd already write for any internal service method, whether the caller is a human-driven UI or a model-generated tool call:

```java
public class PodActionAuthorizer {

    public void authorize(String namespace, String podName, String requestingUserId) {
        if (!allowedNamespacesForUser(requestingUserId).contains(namespace)) {
            throw new UnauthorizedToolCallException(
                "User " + requestingUserId + " is not authorized for namespace " + namespace
            );
        }
        if (!kubernetesClient.podExists(namespace, podName)) {
            throw new InvalidToolCallException(
                "Pod " + podName + " does not exist in namespace " + namespace
            );
        }
    }
}
```

## Layer 3: sandboxing — limiting the blast radius of what execution can even reach

Validation catches malformed or unauthorized requests before execution. Sandboxing is the complementary discipline of limiting what a tool's *implementation* is even capable of doing, so that a validation gap you didn't anticipate still can't cause unbounded damage — the same defense-in-depth principle behind running any internal service with least-privilege credentials rather than relying solely on application-layer checks being perfect. Concretely:

- A tool that reads logs should run with read-only credentials against the log store, at the infrastructure level, not just be *intended* to only read.
- A tool that can restart a pod should be scoped, via real Kubernetes RBAC, to only the namespaces your business-rule validation already restricts it to — so that even a bug in your Java-level authorization check doesn't grant broader access than intended.
- A tool that executes anything resembling a shell command (generally best avoided, per file 1's narrow-tool guidance) should run inside a genuinely isolated execution context if it must exist at all, never with the same privileges as your main application process.

## Returning validation failures back to the model, correctly

When validation fails, the correct response is not to throw an unhandled exception that crashes the interaction — it's to construct a `tool_result` block that reports the failure back to the model as content, following exactly the wire format from Phase 02, file 5, so the model can see what went wrong and potentially recover (asking the user for clarification, trying a different, valid argument):

```java
String errorResult = "Error: namespace 'prod-legacy' does not exist. Valid namespaces are: dev, staging, prod.";
Message toolResultMessage = new Message("user", buildToolResultContent(toolUseId, errorResult));
```

This keeps the conversation coherent and gives the model a genuine chance to self-correct, rather than silently failing or crashing the whole agent turn over what might be an easily fixable, minor argument error.

## Trade-offs and when this matters most

- For read-only, low-consequence tools (checking status, reading logs), schema validation plus light business-rule checks is usually proportionate — heavy sandboxing adds operational complexity without a correspondingly serious risk to mitigate.
- For any tool capable of a state-changing or irreversible action, all three layers are warranted, and the fourth layer — human confirmation, next file — often belongs on top of all of them, not as a replacement for any single one.
- Don't treat schema validation alone as sufficient for anything consequential — it catches malformed shape, not unauthorized or nonsensical *intent*, which is exactly what business-rule validation and sandboxing exist to catch.

## Why this matters next

You now have three layers of defense between "the model requested this" and "this actually executes." For the most consequential class of actions, a fourth layer is often warranted: an explicit human in the loop, before execution happens at all — covered next.
