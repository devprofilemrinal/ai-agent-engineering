# Phase 09 — Orchestration and Multi-Agent Systems

## Why this phase exists

Phase 07 built a single agent capable of iterating on its own, and Phase 08 showed you how to build that same agent faster using a framework. Both phases assumed one agent, with one system prompt, one tool set, and one continuous reasoning loop, handling one task end to end. This phase is about what happens when a single agent's scope becomes too broad for that structure to hold up well — when a task genuinely decomposes into distinct sub-problems that benefit from being handled by differently-scoped, differently-prompted, differently-tooled agents working together, rather than one enormous agent trying to be good at everything at once.

It's worth being direct about why this phase comes *after* Phase 08 rather than being folded into it, and why it's more cautious than typical AI-engineering material tends to be about the appeal of multi-agent systems. Multi-agent architectures are frequently taught and demonstrated as an impressive, almost default next step once you have a working single agent — dividing labor across several specialized agents *feels* like sophisticated engineering. This handbook's position is more measured: a multi-agent system is strictly harder to build, debug, and reason about than a single agent, because you're no longer debugging one non-deterministic system (Phase 00) — you're debugging several non-deterministic systems whose combined, emergent behavior depends on how they communicate and hand off work to each other, which is itself an additional source of non-determinism layered on top. If a single, well-designed agent with a good tool set and a clear system prompt can handle a task, that is very often a better engineering choice than a multi-agent system built for the sake of using the pattern. This phase teaches you the real patterns — supervisor/worker delegation, graph-based orchestration, and role-based teams — and asks you, throughout, to justify *why* a given task actually needs more than one agent, not just how to build one that has several.

This phase deliberately treats LangGraph and CrewAI — the Python ecosystem's dominant multi-agent frameworks — as *patterns* to understand and implement in Java, using Spring beans, explicit state machines, and the tooling from Phases 05 through 08, rather than as libraries you need a Java port of. The reasoning behind this choice: your production target is Java and Spring Boot, and a supervisor/worker pattern or a graph-based orchestration is a genuine architectural idea independent of any specific library's syntax — building it yourself, on top of everything you already know, is both more durable (it won't break when a Python library's API changes) and more legible to the rest of your existing Java codebase's conventions.

## What this phase covers

1. **`01-supervisor-worker-pattern.md`** — a coordinating agent that delegates sub-tasks to specialized worker agents and synthesizes their results, the most common and often most appropriate multi-agent structure for real production tasks.
2. **`02-graph-based-agent-orchestration.md`** — modeling an agent workflow as an explicit state machine/graph with defined nodes and transitions, translating LangGraph's core idea into a Java state-machine implementation, for tasks whose control flow is more complex than a simple delegate-and-synthesize structure.
3. **`03-role-based-agent-teams-crewai-concepts.md`** — CrewAI's role-based framing (agents with defined personas, goals, and backstories collaborating as a "team"), what genuine engineering value this framing adds versus supervisor/worker, and where it's mostly a presentation layer over the same underlying mechanics.
4. **`04-inter-agent-communication-protocols.md`** — the actual mechanics of how agents hand off context, state, and partial results to each other, and the real failure modes (context loss, contradictory partial state, cost multiplication) that emerge specifically from multi-agent communication.
5. **`05-project-multi-agent-research-pipeline.md`** — a supervisor coordinating a search agent and a summarizer agent through an explicit graph, with justification for why this task warrants multiple agents rather than the single research agent from Phase 07.

## Prerequisites

Phase 07 (a single, well-built agent loop is the unit this phase composes multiple of) and Phase 08 (the framework fluency this phase's Java-based pattern implementations assume, plus Phase 04's memory management, since each agent in a multi-agent system has its own memory-scoping concerns).

## What you gain from this phase

The ability to decompose a genuinely complex task into a coordinated set of agents with explicit, debuggable control flow — and, just as importantly, the judgment to recognize when a task does *not* need this, and a single well-scoped agent from Phase 07 or Phase 08 is the better, simpler, cheaper choice. This judgment is what Phase 10's evaluation discipline depends on being able to exercise at all: a multi-agent system you built without a clear justification for its complexity is a multi-agent system you will have a much harder time evaluating, tracing, and maintaining once it's running in production.
