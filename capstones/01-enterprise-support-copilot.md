# Capstone 01 — Enterprise Support Copilot

## The system, as a real product

A mid-sized SaaS company's support team handles several hundred tickets a day across email and a help-desk platform. Response quality varies with agent experience, product documentation is scattered across a wiki, a knowledge base, and old resolved tickets, and new support hires take months to become fully productive. This capstone builds a copilot embedded in the support agents' existing ticketing workflow: given an incoming ticket, it drafts a suggested response grounded in actual product documentation and similar past resolved tickets, can look up a specific customer's account history and current subscription status via internal APIs, and escalates to a human immediately for anything it isn't confident about — it never sends a response to a customer without a human support agent reviewing and approving it first. The users are the company's own support agents, not end customers directly; the business problem is response quality and time-to-resolution, not full automation.

## Components, mapped to handbook phases

- **Document and ticket retrieval (Phase 03)** — a RAG pipeline over product documentation, the internal wiki, and a corpus of past resolved tickets, chunked and embedded per Phase 03's discipline, with retrieval quality evaluated against a golden set of realistic support questions before this component is trusted at all.
- **Customer context memory (Phase 04)** — long-term memory scoped per customer account (not per support agent, and not per anonymous session), storing durable facts about a customer's history that inform tone and context for future tickets — implemented with the multi-tenant metadata-filtering discipline Phase 04, file 3 insisted on, since a support copilot leaking one customer's account details into another customer's ticket draft would be a serious incident.
- **Account and subscription lookup tools (Phase 05)** — narrow, read-only tools against internal APIs (customer account status, subscription tier, recent billing events), with Phase 05's validation and sandboxing applied even though these tools are read-only, since a malformed or unauthorized lookup is still a real risk (a support agent seeing another customer's account data due to a validation gap).
- **Draft response generation with structured confidence scoring (Phase 06)** — the copilot's output is not just a draft response string; it's a structured object including a confidence classification (grounded-in-retrieved-docs, grounded-in-similar-past-ticket, or low-confidence-guess) that determines whether the draft is shown to the human agent as a strong suggestion or flagged prominently as needing extra scrutiny.
- **A bounded reasoning loop, not a full autonomous agent (Phase 07)** — the copilot's task per ticket is narrow enough that a single, tightly-budgeted ReAct loop (retrieve context, check account status if relevant, draft a response) is appropriate; this capstone is a deliberate test of Phase 09's central lesson — resist multi-agent complexity where a single well-scoped agent suffices, and this system should not need a supervisor-worker architecture.
- **Mandatory human-in-the-loop gating (Phase 05, file 4)** — every single draft, regardless of confidence classification, requires explicit human agent approval before anything reaches a real customer; this is a non-negotiable design constraint given the business context, not a configurable option.
- **Full evaluation harness (Phase 10)** — tracing every ticket-processing run, a calibrated LLM-as-judge scoring draft quality against real human-approved responses as the reference standard, and a regression suite covering common ticket categories, since a prompt or retrieval change here directly affects real support agents' daily workflow.
- **Production hardening (Phase 11)** — this system handles real customer account data flowing through prompts, making Phase 10, file 2's safe-logging discipline and Phase 11, file 4's guardrails (specifically against a ticket containing an injection attempt aimed at extracting another customer's data) genuinely load-bearing, not optional.

## Cross-cutting production requirements

- **Observability**: every draft's full trace (which documents were retrieved, which tool calls were made, the confidence classification and rationale) must be reconstructable after the fact, since a support team lead reviewing why the copilot suggested a particular response needs this visibility regularly, not just during incidents.
- **Evaluation**: the golden set for this system should be built directly from real historical tickets and their actual, human-approved resolutions — this is a case where you have unusually good ground truth available, and the evaluation harness should exploit it fully rather than relying only on LLM-as-judge scoring.
- **Guardrails**: specifically defend against a ticket's content being used to attempt cross-customer data exfiltration via prompt injection, given the account-lookup tools this system has access to.
- **Cost control**: response drafting for every incoming ticket is a real, ongoing cost at a few hundred tickets a day — Phase 11, file 3's semantic caching is a strong candidate for the retrieval step specifically, since many support questions are genuinely repetitive.

## A failure scenario this system must handle gracefully

A ticket arrives referencing a product feature that was deprecated last month, and the retrieved documentation is a mix of current and outdated material, because the wiki hasn't been fully cleaned up. The system must not confidently draft a response based on outdated documentation without flagging the possibility — this is a direct instance of Phase 01's hallucination and Phase 03's retrieval-quality concerns compounding: correctly retrieved-but-stale material is a distinct failure mode from irrelevant retrieval, and this capstone's confidence-scoring component (Phase 06) needs an explicit mechanism for surfacing "this is grounded in a source, but the source may be outdated" as a genuinely different signal than either high confidence or low-confidence guessing.

## Suggested build order

Start with the retrieval pipeline (Phase 03) and its evaluation against a golden set built from real historical tickets, since a support copilot with poor retrieval is not worth building further on. Add the account-lookup tools (Phase 05) and confidence-scored structured output (Phase 06) next, since these are what let the system distinguish a well-grounded draft from a guess. Add per-customer long-term memory (Phase 04) once the core drafting loop is solid — it's an enhancement to draft quality, not a prerequisite for the system to function at all. Build the full evaluation harness (Phase 10) before any real support agent sees a draft in their actual workflow, and apply Phase 11's production hardening — especially the guardrails against cross-customer data exposure — before this ever touches real customer account data.
