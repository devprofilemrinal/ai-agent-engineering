# Capstone 02 — Autonomous DevOps Incident Agent

## The system, as a real product

An engineering organization runs dozens of microservices, and on-call engineers are paged for incidents at all hours — many of which turn out to be well-understood, previously-seen failure patterns (a specific pod stuck in a crash loop, a database connection pool exhausted, a downstream dependency timing out) that follow a known diagnostic and remediation playbook. This capstone builds an agent that receives an incoming alert, performs initial triage and diagnosis automatically using real observability tool access, proposes a remediation action grounded in that diagnosis, and executes low-risk, well-understood remediations automatically while requiring explicit human approval for anything consequential — directly extending the DevOps tool agent from Phase 05's project into a full incident-response system with genuine reasoning and orchestration on top.

## Components, mapped to handbook phases

- **A triage agent (Phase 07's ReAct pattern)** — receives the raw alert, classifies its likely category (resource exhaustion, downstream dependency failure, deployment-related regression, unknown/novel), and decides what diagnostic information is needed — this is a single, well-scoped agent, not yet a multi-agent system, since triage is a relatively bounded reasoning task.
- **Diagnostic tools (Phase 05)** — read-only tools against your observability stack: querying recent logs, checking metrics dashboards, checking recent deployment history for the affected service — each narrowly scoped per Phase 05, file 1's guidance, with validation ensuring the agent can only query services and namespaces it's actually authorized to inspect.
- **A remediation-proposal and execution agent, orchestrated via the graph pattern (Phase 09, file 2)** — this is the component that genuinely justifies moving beyond a single agent: the workflow has real conditional branches (if triage classifies the incident as a known pattern with a well-understood playbook, proceed to an automated remediation path; if triage can't confidently classify it, route directly to human escalation without attempting remediation at all) that map naturally onto an explicit state graph rather than an unstructured single loop.
- **Tiered confirmation gating (Phase 05, file 4)** — remediation actions are tiered by consequence: read-only diagnostics require no gate; a pod restart requires an automated approval based on strict pre-defined criteria (only during business hours, only if the affected service's error budget hasn't already been exhausted this month); anything touching production data or scaling infrastructure down requires explicit, real-time human approval, with no automated bypass under any circumstance.
- **Full tracing across the triage-and-remediation graph (Phase 10, file 1)** — every incident's complete diagnostic path, tool calls, and remediation decision must be reconstructable for post-incident review, which on-call teams already expect for any automated or human-driven remediation, making this arguably the single most load-bearing component in the entire capstone.
- **A regression suite built from real historical incidents (Phase 10, file 4)** — a golden set of past incidents with their actual correct diagnosis and remediation as ground truth, used to validate that a change to the triage agent's prompt or the graph's routing logic doesn't silently regress its ability to correctly classify and route known incident patterns.
- **Canary-gated deployment of any change to the agent's playbooks (Phase 11, file 8)** — given that a regression here has real operational consequences (a wrongly-classified incident, an inappropriately-executed remediation), no change to this system's prompts, tool definitions, or graph routing logic should reach production without passing the regression suite from Phase 10 first.

## Cross-cutting production requirements

- **Guardrails specific to this domain (Phase 11, file 4)**: an alert's raw content (log excerpts, error messages) is untrusted input that could, in principle, contain injected text if an attacker had already compromised something upstream enough to influence log output — a genuinely paranoid but not unreasonable threat model for a system with real remediation authority, worth explicit input screening even though the "user" here is an automated alert, not a human typing a request.
- **A dead-simple, always-available manual override**: regardless of how well the automated system performs, on-call engineers must be able to immediately halt any in-progress automated remediation and take over manually, at any point, without needing to understand the agent's internal reasoning first — this is a non-negotiable safety requirement given the domain, and should be tested explicitly, not just assumed to work.
- **Audit logging with real retention requirements**: unlike Capstone 01, this system's actions have direct operational consequences, and many organizations have compliance requirements around change and incident management that this system's logging (Phase 10, file 2) needs to satisfy, not just support debugging.

## A failure scenario this system must handle gracefully

The triage agent classifies an incident as a known, low-risk pattern (a stateless service pod crash-looping, historically resolved by a simple restart) and proceeds down the automated remediation path — but the diagnostic tools reveal, on closer inspection mid-loop, that the crash-loop is actually caused by a bad configuration pushed in a very recent deployment, not the transient resource issue the initial classification assumed. The system must be capable of recognizing, from the diagnostic tool results themselves, that its initial classification was wrong and re-route to human escalation rather than blindly executing a restart that will not fix a configuration-caused crash loop and will simply repeat the same failure — this is a direct test of whether the graph-based orchestration (Phase 09, file 2) genuinely includes the kind of re-evaluation and re-routing capability that file argued was necessary for any graph with a real conditional branch, versus a rigid, one-way pipeline that commits to its first classification regardless of what subsequent steps reveal.

## Suggested build order

Start with the diagnostic tools (Phase 05) and a single triage agent (Phase 07) operating read-only, with no remediation capability at all — validate that triage classification is actually reliable against your historical incident golden set (Phase 10, file 4) before giving the system any ability to act. Add the graph-based orchestration (Phase 09, file 2) with the automated remediation path next, starting with the single lowest-risk remediation action (a simple, clearly-scoped restart) and its tiered confirmation gate (Phase 05, file 4). Build the full tracing and audit logging (Phase 10, file 1 and Phase 10, file 2) before this system executes any remediation against real infrastructure, even in a staging environment. Expand the remediation action set and confirmation tiers only after the initial narrow scope has been running reliably and its regression suite (Phase 10, file 4) has real historical incident coverage — this is a system where scope creep before reliability is proven is a genuinely dangerous mistake, not just an engineering inefficiency.
