# Capstone 03 — Multi-Agent Financial Research Platform

## The system, as a real product

An investment research team needs to produce structured research briefs on companies or sectors — pulling recent financial filings, analyzing key metrics against historical trends, and synthesizing findings into a report an analyst can review and refine, rather than write from scratch. Unlike Capstone 01's support copilot, this task genuinely decomposes into distinct specialties — data retrieval, quantitative analysis, and narrative writing are meaningfully different skills requiring different tool access and different reasoning styles — making this the capstone where Phase 09's multi-agent orchestration is most clearly justified, provided the team building it still does the honest cost/benefit justification Phase 09's opening file demanded, rather than assuming decomposition is automatically correct just because the domain sounds complex.

## Components, mapped to handbook phases

- **A data-retrieval agent (Phase 07's ReAct pattern, with Phase 05 tools)** — has tools for querying financial data APIs, fetching recent filings, and searching for relevant news; its system prompt and reasoning are oriented purely around finding and validating source material, with explicit instructions against performing analysis or drawing conclusions itself, per Phase 09, file 1's guidance on narrow, non-overlapping worker scope.
- **An analysis agent (Phase 07, with different tools than the retrieval agent)** — receives gathered data via an explicit handoff contract (Phase 09, file 4's `AgentHandoff` pattern) and performs quantitative analysis: computing ratios, comparing against historical trends, flagging anomalies — with no external search tools of its own, so it cannot silently go fetch its own additional data outside of what the retrieval agent explicitly gathered and handed off, keeping the division of responsibility real rather than nominal.
- **A structured findings format between retrieval and analysis (Phase 06)** — the retrieval agent's output to the analysis agent should be schema-constrained structured data (source, date, key figures extracted), not free-form prose, so the analysis agent has reliably parseable input rather than having to re-extract facts from another agent's prose summary — a direct, deliberate application of Phase 06's reliability discipline at an inter-agent boundary, not just at the user-facing output boundary.
- **A writing agent (Phase 07)** — takes the analysis agent's structured findings and produces a polished, narrative research brief; like the retrieval agent, it should have no independent data-gathering or analysis capability, so a factual error can be traced back to either the retrieval or analysis stage, not obscured by the writing agent potentially introducing or altering figures during narrative composition.
- **A supervisor coordinating the three, with graph-based branching (Phase 09, files 1 and 2)** — a relatively flat supervisor-worker delegation for the common case, with at least one genuine conditional branch: if the analysis agent flags that the retrieved data is insufficient or contradictory (e.g., conflicting figures from two sources), the graph should route back to the retrieval agent for clarification rather than forcing the writing agent to synthesize a report from unresolved, contradictory findings.
- **Semantic evaluation with a strong emphasis on factual grounding (Phase 10, file 3)** — the LLM-as-judge criteria for this system should specifically include "is every quantitative claim in the final report traceable to a specific figure in the retrieval agent's structured findings," which is a more checkable, less purely subjective criterion than general "quality," and should ideally be implemented as a hybrid: a deterministic check cross-referencing cited figures against the structured retrieval output (Phase 06-style validation) supplemented by LLM-as-judge scoring only for genuinely subjective qualities like narrative clarity.
- **Full cost attribution across all three agents (Phase 09, file 1's nested-cost-tracking discussion, and Phase 10, file 5's dashboards)** — given three separately-invoked agents per report, understanding which stage is the dominant cost driver is directly actionable: if the retrieval agent's cost dominates because it's making excessive redundant searches, that's a different fix (better tool scoping, Phase 05, file 1) than if the analysis agent is the dominant cost due to an unnecessarily long reasoning chain (worth revisiting its budget, Phase 07, file 4).

## Cross-cutting production requirements

- **Evaluation with real financial-domain rigor**: given that factual errors in financial analysis carry genuine professional consequence for an analyst relying on this system, the deterministic figure-cross-referencing check described above is not optional polish — it should be treated as a mandatory gate before any report is considered complete, more load-bearing than the LLM-as-judge narrative-quality scoring.
- **Explicit source citation in every output**: every report must trace every material claim back to a specific source document and figure, extending Phase 03, file 8's source-citation extension exercise into a mandatory requirement rather than an optional add-on, given the domain's stakes.
- **Cost monitoring granular enough to justify the multi-agent design**: per Phase 09's central demand, this capstone should include a genuine, measured comparison — even a rough one — of this three-agent pipeline's cost and quality against a single well-scoped generalist agent attempting the same task, to actually validate (not just assume) that the decomposition was worth its overhead.

## A failure scenario this system must handle gracefully

The retrieval agent gathers two figures for the same metric (say, quarterly revenue) from two different sources that genuinely disagree — perhaps one source hasn't yet incorporated a recent restatement. The analysis agent must detect this contradiction rather than silently picking one value and proceeding (a real risk given that averaging or arbitrarily selecting between conflicting figures, per Phase 01's generation mechanics, is a highly plausible failure mode for a model asked to "analyze the revenue figure" without being explicitly instructed to check for exactly this kind of discrepancy first). The correct behavior is the graph's conditional branch back to the retrieval agent, requesting clarification or a more authoritative source specifically for the contradicted figure, rather than the pipeline proceeding to a confident-sounding report built on an unresolved factual conflict.

## Suggested build order

Build and validate the retrieval agent alone first, with its structured-output contract (Phase 06) to the (not-yet-built) analysis stage clearly defined, since poor retrieval undermines everything downstream regardless of how good the analysis and writing agents are. Add the analysis agent next, testing it directly against manually-constructed structured findings (bypassing the retrieval agent initially) so you can validate its quantitative reasoning in isolation before compounding it with retrieval's own potential errors. Add the writing agent and the full supervisor/graph orchestration only once retrieval and analysis are each independently solid. Build the deterministic figure-cross-referencing evaluation check (Phase 06-style, applied to this system's final output) before ever treating this system's reports as something an analyst should trust without independent verification — and run the honest multi-agent-versus-single-agent cost/quality comparison this brief calls for before considering the three-agent architecture validated rather than merely assumed.
