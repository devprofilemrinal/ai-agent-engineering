# Capstone 04 — AI Code Review and Refactoring Agent

## The system, as a real product

An engineering team wants automated first-pass code review on every pull request — not to replace human reviewers, but to catch common issues (style inconsistencies, missed edge cases, deviations from documented architecture patterns, potential bugs a static analyzer alone wouldn't flag) before a human reviewer spends time on them, and to propose concrete refactoring suggestions grounded in the team's own conventions rather than generic best practices. This capstone is, deliberately, the one most directly relevant to your own daily work as a Java backend engineer — the system under review and the system doing the reviewing are both things you already have deep, direct expertise in, which makes this an unusually good capstone for evaluating your own work honestly, since you're positioned to judge its output quality with more authority than any of the other three capstones' domains.

## Components, mapped to handbook phases

- **Retrieval over the team's own conventions and architecture docs (Phase 03)** — a RAG pipeline over the codebase's own documented architecture decisions, style guides, and past review comments (if available), so the agent's review comments are grounded in this specific team's actual conventions, not generic advice a model might produce from training data alone — directly testing Phase 03's core lesson that retrieval exists to ground generation in facts the model doesn't reliably have memorized, applied here to organization-specific conventions rather than general documentation.
- **Static analysis tool integration (Phase 05)** — a tool wrapping your existing static analysis tooling (whatever your team already uses), so the agent can request and incorporate deterministic findings rather than trying to detect every issue through generation alone — a direct, practical instance of Phase 06's broader lesson that a deterministic check is preferable to a probabilistic one wherever one is available, applied at the tool-design level rather than the output-validation level.
- **Structured review comments with severity classification (Phase 06)** — the agent's output is not free-form review prose; it's a structured list of findings, each with a file/line reference, a severity classification (blocking, suggestion, nitpick), and a rationale — schema-constrained per Phase 06's discipline, both because this maps naturally onto how review comments actually get posted to a PR via API, and because structured severity classification is what lets a human reviewer triage the agent's findings efficiently rather than reading a wall of undifferentiated prose.
- **A bounded ReAct loop per file or per logical change, not one unbounded loop per entire PR (Phase 07)** — for a large PR touching many files, treating the entire review as one single agent loop risks exactly the context-window and buried-fact problems Phase 01 and Phase 04 warned about; a more robust design processes the PR as a set of bounded sub-tasks (one loop per file or per logical grouping of related files), each with its own budget, rather than one enormous loop trying to hold an entire large PR's context at once.
- **A refactoring-suggestion mode requiring explicit opt-in (Phase 05, file 4)** — this system should default to read-only review comments; actually proposing and applying a refactoring change (modifying code, not just commenting on it) is a more consequential action that should require the PR author's explicit request and review before any suggested change is applied, following Phase 05, file 4's tiered-confirmation logic directly.
- **Evaluation against your own team's historical review comments (Phase 10, file 3 and file 4)** — this capstone has an unusually strong source of ground truth available: past PRs with real human review comments already attached. A golden set built from real historical PRs, comparing the agent's generated review findings against what human reviewers actually flagged on the same code, gives you a genuinely rigorous evaluation basis rather than relying purely on LLM-as-judge scoring without a strong human-generated reference.
- **Prompt/config versioning tied to the codebase's own conventions evolving (Phase 11, file 7)** — as the team's style guide or architecture patterns change over time, the retrieval corpus and the agent's grounding needs updating; treating this as a versioned configuration change (not an ad hoc edit) means you can track exactly which "understanding" of the team's conventions produced a given review, useful when a convention itself is later revised and old reviews need to be understood in their original context.

## Cross-cutting production requirements

- **Precision matters more than recall here, arguably more than in any other capstone**: a code review agent that produces many low-value or incorrect comments quickly loses developer trust and gets ignored entirely — a distinct product-adoption risk beyond the usual correctness concerns, meaning Phase 10's evaluation should specifically track false-positive rate (findings a human reviewer would disagree with or find unhelpful) as a first-class metric, not just overall "quality."
- **Fast enough to fit into a real PR workflow**: developers expect review feedback within minutes of opening a PR, not the next day — this makes Phase 11, file 5 and file 6's rate-limiting and scaling discipline directly relevant, since review requests can spike when multiple PRs are opened around the same time (end of a sprint, for instance), and Phase 01's latency mechanics (output length driving latency) argue for keeping each bounded per-file review loop's expected output reasonably concise.
- **Guardrails against a PR's content itself being adversarial**: while a less likely threat model than Capstone 02's, a PR could in principle contain a code comment or string literal crafted to look like an instruction to the reviewing agent — worth at least a lightweight input guardrail (Phase 11, file 4) given that this system processes arbitrary, sometimes external, contributor-authored content.

## A failure scenario this system must handle gracefully

A PR modifies a piece of code in a way that's technically correct and passes all existing tests, but subtly violates an architectural convention documented in a design doc that was retrieved as part of this system's RAG corpus — however, the retrieved chunk (Phase 03) happens to be from an older version of that document, since the corpus hasn't been re-ingested since a recent documentation update loosened that particular convention. The system should not confidently flag this as a blocking violation of a rule that no longer applies — this is a direct instance of Capstone 01's stale-retrieval failure scenario, recurring here in a different domain, and it argues for the same kind of confidence/staleness signal discussed there: a review comment citing a specific documented convention should ideally note the source document's retrieval date or version, so a human reviewer can quickly recognize and dismiss a comment grounded in outdated guidance, rather than the system presenting stale-but-confident findings indistinguishable from current, accurate ones.

## Suggested build order

Start with the static analysis tool integration (Phase 05) and structured output format (Phase 06) alone, without retrieval or a full reasoning loop yet — validate that the agent can correctly incorporate and report deterministic findings before adding the harder, less deterministic layer of convention-grounded review commentary. Add the RAG pipeline over your team's actual conventions and architecture docs (Phase 03) next, and build the historical-PR-based golden set (Phase 10, file 4) as early as possible, since it's this capstone's most valuable evaluation asset and is available to you immediately, unlike the other capstones' evaluation data. Add the per-file bounded reasoning loop (Phase 07) once retrieval and static-analysis integration are both independently solid, and only add the refactoring-suggestion (as opposed to comment-only) capability once the review-comment quality has been validated against your historical golden set and you're confident enough in the system's precision to let it propose actual code changes, gated behind explicit developer opt-in per Phase 05, file 4.
